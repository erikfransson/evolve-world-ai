# bf16 brain weights (halve the weight bandwidth)

Branch `pl-bf16`. Rejected, the branch holds this note only. Machine load 8-14 on 8 cores, so min over 15 runs and same-process ratios are quoted.

## Step 1: is the brain kernel memory-bound?
Live mix: 3200 brains, 800 of each founder (shapes `55x12x12x4`, `55x16x16x4`, `93x24x24x24x24x18`, `55x12x12x4`), 6.0 M weights, 24 MB of f32. Random per-copy perturbations of the founder genomes, sparse random inputs (30% of rays hit), one `forwardSlots` call over all slots.
Control: same call with the weight pointer of slot c redirected to slot c mod 100 (100 blocks, about 0.75 MB, fits the 1.25 MB L2 share), each slot keeping its own input and output vector, so only the weight traffic changes.

| Run (min / median of 15 ms) | Distinct blocks | 100 shared blocks | Shared / distinct |
|-----------------------------|-----------------|-------------------|-------------------|
| base, 3 rounds              | 5.46 / 5.66, 5.41 / 5.86, 5.22 / 5.41 | 3.92 / 4.08, 3.89 / 4.22, 3.79 / 4.16 | 0.72 |
| base, later pairs           | 5.26-5.40 | 3.84-4.19 | 0.72-0.76 |

The kernel is not purely compute-bound: about 28% (1.4-1.5 ms of 5.4) goes away when the weights sit in L2. The remainder, 3.9 ms (0.65 ns per weight), stays and is compute or latency. So the most bf16 could save is half of that 28%, about 0.7 ms, which is 4.8% of the 15.24 ms tick, and only if the widening costs nothing.

## Step 2: bf16 prototype
Kernel copy of weights and biases as bf16 (round to nearest even of the f32 bits, set() writes u16, input and output vectors stay f32 behind the 16-byte padded weights). In `brain.wat` every weight and bias load became `v128.load16x4_u` (pmovzxwd from memory) plus `i32x4.shl 16`. The genome stays f32.

| Variant | Distinct blocks (min ms) | 100 shared blocks (min ms) | Verdict |
|---------|--------------------------|----------------------------|---------|
| base f32 | 5.26-5.46 | 3.79-4.19 | |
| bf16, load16x4_u + shl (3 pairs, interleaved) | 5.40-5.67 | 4.35-4.66 | no gain |
| bf16, 16-byte load + `i8x16.shuffle` against zero in the 4-vector branch | 7.0-7.1 | 6.4-6.9 | 30% slower, dropped |

The widening costs about 0.5 ms (shared case 3.9 to 4.4 ms) and cancels the memory saving (distinct case unchanged within noise, 5.4 vs 5.4-5.6). The 50% extra ALU per weight vector (load+shift instead of load) lands on the same unit mix the multiply-add already uses.
Output difference with `node src/wasmBench.ts --sizes 3000`: max abs diff to the JS Brain 3.3e-3 (default plan) and 4.5e-3 (large plan), against about 1e-6 for f32 (relative 2^-9 per weight). That would change the fingerprint and need the behaviour check for no gain.

## Verdict
Reject. The gain gate (5% of the tick) is not met, the kernel is neutral, so the `liveBench` pairs and the 600 s population check were not run. The weight stream is only 28% of the kernel and the widening eats it. Prototype diff kept outside the repo (scratchpad `bf16/bf16-prototype.diff`).
